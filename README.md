# Codzee Code Review Lab — Employee Salary API

A deliberately small Spring Boot backend for managing employees and their current salary. It is the
baseline codebase for evaluating AI code review on focused pull requests, so it favors clear business
rules, real tests and boring, readable code over features.

**In scope:** employee create / read / paginated list / update, current salary get / set, salary
summaries, validation and consistent error responses.
**Out of scope:** authentication and authorization, salary history, payroll, deletion, frontend.

## Architecture

Feature packages under `io.codzee.reviewlab`, each layered controller → service → repository:

```
src/main/java/io/codzee/reviewlab/
├── CodzeeReviewLabApplication.java
├── common/     GlobalExceptionHandler (RFC 7807 problem responses), ResourceNotFoundException, ConflictException
├── employee/   Employee (entity), EmployeeRepository, EmployeeService, EmployeeController, EmployeeRequest/Response
└── salary/     Salary (entity), SalaryRepository, SalaryService, SalaryController,
                SalaryRequest/Response, SalarySummaryRequest, SalarySummary
src/main/resources/
├── application.yml
└── db/migration/   V1__create_employee_table.sql, V2__create_salary_table.sql
```

- **Controllers** only handle HTTP: binding, `@Valid`, status codes, `Location` headers.
- **Services** own the business rules and transaction boundaries (read-only by default, read-write on
  mutations). They also validate their input with the same Bean Validation constraints the DTOs
  declare, so the rules hold for non-HTTP callers. The rules are written once, on the DTOs.
- **Repositories** are plain Spring Data JPA interfaces.
- **DTOs** (Java records) form the API contract. Entities are never serialized.
- **Errors** are centralized in `GlobalExceptionHandler`, which returns Spring's `ProblemDetail`
  (RFC 7807) and never includes stack traces, exception class names or SQL.

## Business rules

### Employee
- `id` is generated by the database.
- `name`: required, not blank, at most 100 characters.
- `email`: required, well-formed, at most 254 characters, **unique**. Emails are stored lower-cased,
  so uniqueness is case-insensitive (`Ada@Example.com` and `ada@example.com` conflict).
- `department`: required, not blank, at most 100 characters (free text).
- `PUT /api/employees/{id}` is a full update: all three fields are required.
- The list endpoint is paginated: default page size 20, sorted by `id`, maximum page size 100.
- Employee responses never contain salary data.

### Salary
- Each employee has at most **one current salary**. The `salary` table's primary key is the employee
  id, so there is no ambiguity and no history. Setting a salary replaces the previous value.
- `PUT /api/employees/{id}/salary` creates or replaces the current salary in one transaction and is
  idempotent. The employee must exist.
- `amount`:
  - Required and strictly greater than `0`.
  - At most **2 decimal places**. `10.555` is rejected, never rounded.
  - At most 13 integer digits, so the maximum is `9999999999999.99`, which fits `DECIMAL(15,2)`.
  - Stored and returned with scale 2 (`1500.5` → `1500.50`).
- `currency` must be sent explicitly and must be `USD`, the only supported currency. Any other value
  is rejected, so currencies are never mixed.
- `updatedAt` is the UTC instant the salary was last set (microsecond precision).
- All money arithmetic uses `BigDecimal`. `double` and `float` are never used for money.

### Salary summary
- Input: `employeeIds`, required, at most 1000 ids, no null elements. Duplicate ids are counted
  once, and ids that don't exist or have no salary are skipped.
- Output:
  - `employeeCount`: how many of the requested employees have a salary.
  - `totalSalary`: exact sum, scale 2.
  - `averageSalary`: `total / count`, rounded to 2 decimals with `HALF_EVEN` (banker's rounding).
  - `currency`.
- Empty input, or no matching salaries, returns `0`, `0.00`, `0.00`.
- If stored salaries ever had different currencies, the summary refuses to add them up and fails
  instead.

## Database schema

```
employee                                   salary
─────────────────────────────────          ─────────────────────────────────────────────
id          BIGINT  PK AUTO_INCREMENT  ◄── employee_id BIGINT        PK, FK → employee.id
name        VARCHAR(100) NOT NULL          amount      DECIMAL(15,2) NOT NULL, CHECK (amount > 0)
email       VARCHAR(254) NOT NULL UNIQUE   currency    VARCHAR(3)    NOT NULL
department  VARCHAR(100) NOT NULL          updated_at  DATETIME(6)   NOT NULL  (UTC)
```

Flyway (`src/main/resources/db/migration`) owns the schema, and Hibernate only validates it. The
relationship is a unidirectional, lazily fetched one-to-one from `Salary` to `Employee`.

## Configuration

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

Edit `.env` and replace the placeholder passwords. `.env` is git-ignored, so never commit it.

| Variable           | Used by          | Default in `.env.example` |
|--------------------|------------------|---------------------------|
| `DB_HOST`          | app              | `localhost`               |
| `DB_PORT`          | app, Compose     | `3307`                    |
| `DB_NAME`          | app, Compose     | `reviewlab`               |
| `DB_USERNAME`      | app, Compose     | `reviewlab`               |
| `DB_PASSWORD`      | app, Compose     | placeholder               |
| `DB_ROOT_PASSWORD` | Compose only     | placeholder               |

The host port defaults to **3307**, so it doesn't clash with a locally installed MySQL on 3306. It
is bound to `127.0.0.1` only. The app reads the same `.env` file through
`spring.config.import=optional:file:.env[.properties]`, and real environment variables take
precedence over it.

## Running MySQL with Docker Compose

```bash
docker compose up -d --wait     # starts MySQL 8.4 and blocks until the health check passes
```

Verify health:

```bash
docker compose ps               # STATUS should show "(healthy)"
docker inspect -f '{{.State.Health.Status}}' reviewlab-mysql
```

Stop **without losing data** (the named volume `codzee-review-lab_mysql-data` is kept):

```bash
docker compose stop             # stop the container
docker compose down             # or: remove container and network, keep the volume
```

**Intentionally delete all database data:**

```bash
docker compose down -v          # removes the volume as well; irreversible
```

## Running the application

```bash
./mvnw spring-boot:run          # Windows: mvnw.cmd spring-boot:run
```

Or build and run the jar:

```bash
./mvnw package
java -jar target/codzee-code-review-lab-0.1.0-SNAPSHOT.jar
```

Run the app from the repository root so it can find `.env`. On startup, Flyway applies the
migrations and the API listens on `http://localhost:8080`. Flyway logs a "Flyway upgrade recommended:
MySQL 8.4 is newer than this version of Flyway" warning. That comes from the Spring Boot-managed
Flyway version and is harmless for this schema.

## Running tests

All tests use in-memory H2 in MySQL mode with the real Flyway migrations (`src/test/resources/application-test.yml`).
They don't need Docker and never touch your local MySQL data.

```bash
./mvnw test                                      # all 90 tests
./mvnw test -Dtest='*ServiceTest*'               # unit tests (Mockito, no Spring context)
./mvnw test -Dtest='*ControllerTest'             # API tests (MockMvc, @WebMvcTest)
./mvnw test -Dtest='*RepositoryTest'             # persistence tests (@DataJpaTest + H2 + Flyway)
./mvnw test -Dtest=EmployeeSalaryIntegrationTest # end-to-end, full context, no mocks
```

On Windows use `mvnw.cmd` instead of `./mvnw`.

## Coverage report

```bash
./mvnw verify
```

`verify` runs the tests, writes the JaCoCo report and fails the build if line or branch coverage
drops below 80%. Open `target/site/jacoco/index.html` in a browser to inspect it. At the time of
writing, line coverage is 98.7% and branch coverage is 100%. The only uncovered lines are in `main()`.

## API

Base URL `http://localhost:8080`. All bodies are JSON. The examples below were captured from the
running application against MySQL.

| Method | Path                               | Success | Errors             |
|--------|------------------------------------|---------|--------------------|
| POST   | `/api/employees`                   | 201     | 400, 409           |
| GET    | `/api/employees/{id}`              | 200     | 400, 404           |
| GET    | `/api/employees?page=&size=&sort=` | 200     | 400                |
| PUT    | `/api/employees/{id}`              | 200     | 400, 404, 409      |
| GET    | `/api/employees/{id}/salary`       | 200     | 400, 404           |
| PUT    | `/api/employees/{id}/salary`       | 200     | 400, 404           |
| POST   | `/api/salaries/summary`            | 200     | 400                |

### Create an employee

```http
POST /api/employees
{"name": "Ada Lovelace", "email": "Ada@Example.com", "department": "Engineering"}
```
```http
201 Created
Location: http://localhost:8080/api/employees/1

{"id": 1, "name": "Ada Lovelace", "email": "ada@example.com", "department": "Engineering"}
```

### Get, list and update employees

```http
GET /api/employees/1
200 {"id": 1, "name": "Ada Lovelace", "email": "ada@example.com", "department": "Engineering"}

GET /api/employees?page=0&size=1
200 {"content": [{"id": 1, "name": "Ada Lovelace", "email": "ada@example.com", "department": "Engineering"}],
     "page": {"size": 1, "number": 0, "totalElements": 2, "totalPages": 2}}

PUT /api/employees/1
{"name": "Ada King", "email": "ada@example.com", "department": "Research"}
200 {"id": 1, "name": "Ada King", "email": "ada@example.com", "department": "Research"}
```

`sort` accepts employee fields, for example `sort=name,desc`.

### Set and get the current salary

```http
PUT /api/employees/1/salary
{"amount": 85000.5, "currency": "USD"}
```
```http
200 OK
{"employeeId": 1, "amount": 85000.50, "currency": "USD", "updatedAt": "2026-10-11T18:45:59.187891Z"}
```

`GET /api/employees/1/salary` returns the same shape.

### Salary summary

```http
POST /api/salaries/summary
{"employeeIds": [1, 2, 999]}
```
```http
200 OK
{"employeeCount": 2, "totalSalary": 177000.50, "averageSalary": 88500.25, "currency": "USD"}
```

`{"employeeIds": []}` returns `{"employeeCount": 0, "totalSalary": 0.00, "averageSalary": 0.00, "currency": "USD"}`.

### Error responses

Every error uses `application/problem+json`:

```json
// 400: Bean Validation failure (field errors sorted by field)
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "Request validation failed",
 "instance": "/api/employees",
 "errors": [{"field": "email", "message": "must be a well-formed email address"},
            {"field": "name",  "message": "must not be blank"}]}

// 400: invalid salary
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "Request validation failed",
 "instance": "/api/employees/1/salary",
 "errors": [{"field": "amount",   "message": "numeric value out of bounds (<13 digits>.<2 digits> expected)"},
            {"field": "currency", "message": "must be USD, the only supported currency"}]}

// 400: malformed JSON / unknown sort property
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "Failed to read request", "instance": "/api/employees"}
{"type": "about:blank", "title": "Bad Request", "status": 400, "detail": "Unknown sort property: salary", "instance": "/api/employees"}

// 404
{"type": "about:blank", "title": "Not Found", "status": 404, "detail": "Employee 999 not found", "instance": "/api/employees/999"}
{"type": "about:blank", "title": "Not Found", "status": 404, "detail": "Employee 1 has no salary", "instance": "/api/employees/1/salary"}

// 409
{"type": "about:blank", "title": "Conflict", "status": 409, "detail": "An employee with email ada@example.com already exists", "instance": "/api/employees"}

// 500: details are logged server-side only
{"type": "about:blank", "title": "Internal Server Error", "status": 500, "detail": "An unexpected error occurred", "instance": "..."}
```

## Known limitations and future improvements

- **No authentication or authorization.** Anyone who can reach the API can read and change salaries.
  This is out of scope for the baseline, and any real deployment needs it.
- **The summary can reveal an individual salary.** Requesting a summary for a single id returns that
  employee's exact salary. Without auth this adds nothing beyond `GET /salary`, but once access
  control exists, a minimum group size (or summary-only permissions) should be considered.
- **Single currency (USD).** Multi-currency support would need per-currency summaries or an
  exchange-rate policy.
- **The summary is computed in memory** over at most 1000 loaded rows. A database aggregate
  (`SUM`/`COUNT`) would avoid loading entities.
- **Concurrency:** two simultaneous first-time `PUT .../salary` calls for the same employee race on
  the primary key, and the loser gets a 409. Updates are last-write-wins, with no optimistic locking.
- **Email validation** follows Hibernate Validator's `@Email`, which accepts addresses without a
  top-level domain (for example `ada@localhost`).
- **Tests use H2 in MySQL mode**, not MySQL itself. The migrations and the application were checked
  manually against MySQL 8.4. A Testcontainers profile would automate that check.
